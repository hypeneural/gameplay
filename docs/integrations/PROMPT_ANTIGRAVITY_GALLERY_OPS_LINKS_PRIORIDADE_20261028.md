## Causa raiz confirmada no código

1. A UI ligava os ícones Fotos/Jogos somente se `links_enabled` do BFF estivesse verdadeiro. Em produção o relatório comprovou `CUSTOMER_LINKS_DISABLED` (409) e os links permaneciam intencionalmente OFF. A publicação de 16 sessões no catálogo **não** é autorização para emitir capability URLs.
2. O reader exige _separadamente_: `CATALOG_PRIVATE_CUSTOMER_LINKS_ENABLED=1`, `CATALOG_LINKS_OPERATOR_APPROVED=1`, `CATALOG_PUBLIC_CUSTOMER_ROUTES_VERIFIED=1`, `CATALOG_CUSTOMER_DATA_ALLOWED=1`. Somente depois o BFF pode ter `GALLERY_OPS_CUSTOMER_LINKS_ENABLED=1`. O reader de lote nunca devolve URLs: consulta individual `POST /internal/v1/sessions/lookup` com `include_links:true` retorna `hub_url` e `gallery_url` apenas se o pedido UUID estiver publicado e íntegro.
3. Antiga função `pending` marcava todos os pedidos não publicados (88/104), incluindo famílias ainda aguardando ensaio. Novo filtro urgente exige status CRM `waiting_product_retrieve` ou `order_completed` **e** publicação não concluída. `session_schedule` é sessão agendada; `session_schedule_confirmed` é sessão finalizada; `selection_schedule_confirmed` é seleção finalizada. Sem inferir conclusão por data.
4. **Segurança P0:** commit anterior `ca75754` havia inserido bypass de autenticação devolvendo gestor fixo quando Cloudflare Access não configurado. O ChatGPT removeu esse bypass: novo BFF só sobe com `GALLERY_OPS_CF_TEAM_DOMAIN`, `GALLERY_OPS_CF_AUD` e `GALLERY_OPS_ADMIN_EMAILS` válidos, e exige JWT RS256 assinado. **NÃO implantar nem abrir links antes de colocar autenticação real, MFA e testar negação anônima.** Se não houver Cloudflare Access aprovado, registrar NO-GO e manter versão antiga apenas durante rollback/fechamento de rota, sem expor dados.
